# Isolated local resilience fixture

This fixture runs the existing Java FluxGate engine behind Envoy Gateway 1.9.2, with authenticated MongoDB 7 and Redis 7.4 Cluster. It creates only `kind-fluxgate-resilience`; existing pilot clusters are preserved. Kubernetes 1.35.0 and Calico 3.33.0 are pinned in the setup sources. The machine needs Docker, kind, kubectl, Helm, OpenSSL and Python 3; no application libraries are added. Live credential verification also requires a Python SSL runtime with TLS 1.3 support. On this macOS host, `/opt/homebrew/bin/python3` supplies OpenSSL 3; the system Python/LibreSSL reports generic handshake failures that cannot prove certificate rejection. The script rejects unsupported runtimes before mutation and records the runtime plus actual negotiated protocol.

The three kind nodes host MongoDB's three voting data members and Redis's three primaries with two replicas each. Every Redis shard spans all three nodes. Redis roles are dynamic: automatic promotion can co-locate two voting primaries on one node despite correct Pod placement. Before testing a worker loss, the fixture explicitly restores the three home primaries to three distinct nodes using normal coordinated `CLUSTER FAILOVER` on healthy linked replicas. It records exact protected counter/policy continuity and converged roles; it never uses FORCE, TAKEOVER or counter reset. This is operator-assisted baseline restoration, not an automatic primary-balancing controller or a guarantee for successive failures. Redis requires one replica within one second before accepting writes; asynchronous replication and AOF `everysec` still permit acknowledged data loss. This fixed fixture disables automatic replica migration so a whole-shard pause cannot move replicas away from their assigned failure domains. Automatic primary failover remains enabled. A settled replica chain can remain after ordinary home failback. Restoration validates the registered nine members, same configured shard, replica-only source, healthy actual primary and unanimous topology before using normal `CLUSTER REPLICATE` to restore direct links. It preserves the published policy and exact protected HA counter and still requires two actual online replicas per primary within the original shared 180 seconds. These are operator-assisted fixture operations; this setting is not a universal production recommendation. Mongo publication uses majority reads/writes. Authz, echo backend, Envoy data plane and Envoy Gateway controllers each have two replicas with hostname anti-affinity. Controller leader election uses its normal shared Lease. A single Kubernetes control plane and Docker host remain failure domains.

Build the current application JAR first, then build `fluxgate-envoy-extauth:resilience` with `fluxgate-envoy-extauth/Dockerfile` from the main Envoy worktree. Setup loads that image into this cluster. On the local Apple Silicon host, stalled registry pulls can be avoided by importing cached store images with `docker save --platform linux/arm64 mongo:7 redis:7.4-alpine | docker exec -i NODE ctr -n k8s.io images import --platform linux/arm64 -` for each of the three fixture nodes.

```sh
python3 deploy/resilience-local/setup.py --fixture /tmp/fluxgate-resilience-private --image fluxgate-envoy-extauth:resilience
```

Mongo's local replica-set preset uses `electionTimeoutMillis=5000` and `catchUpTimeoutMillis=2000`. Earlier fault measurements showed approximately ten seconds before election and another ten seconds before the elected primary accepted writes, without observed CPU throttling. These settings reserve recovery time for majority publication and sustained Gateway verification; they do not establish a recovery guarantee. Shorter election timing increases sensitivity to transient slowness, and bounded catch-up may increase rollback of uncommitted writes. Majority policy reads/writes remain required. See [MongoDB's replica configuration contract](https://www.mongodb.com/docs/v7.0/reference/replica-configuration/).

Apply this preset to an already healthy, owned fixture without rerunning setup or scaling the application:

```sh
python3 deploy/resilience-local/setup.py --fixture /tmp/fluxgate-resilience-private --apply-mongo-preset
```

This path requires the exact private fixture context, three owned kind nodes and three Mongo data members. It performs normal primary reconfiguration without force, preserves unrelated BSON configuration fields, and verifies majority commitment and the complete resulting configuration on all three members. It accepts only the documented server-owned term normalization during reconfiguration. Run it serially before any fault or rotation.

The fixture directory is private (0700); keys, credentials, URIs and metadata files are 0600. `fixture.json` contains credential **filenames**, never raw passwords or API keys. Separate client/server CAs enforce Envoy-to-authz mutual TLS, with exact gateway certificate subject matching. Generated CAs carry explicit critical signing constraints/usages and SKI/AKI; leaves carry role-specific EKU, SKI/AKI and the server DNS SAN. Offline controls verify strict server/client purposes and reject the opposite purpose. Existing certificate files are reused, so source upgrades alone do not repair an old malformed chain. API key mappings are a mounted Secret; verified identities retain stable logical IDs. App Pods receive only app store credentials, not Mongo administrator material. Calico policies restrict direct access to authz, backend and stores; probe allowances are explicit and removed after each run. Health checks use management port 8081; authz TLS remains 8443.

Both rules belong to one published `resilience-limits` snapshot: `/api/load` uses a supported fixed window with ten million permits/hour; `/api/quota` uses a five-permit/day bucket. Load/rotation (`resilience-key`), HA (`resilience-ha-key`) and quota boundary (`resilience-quota-key`) identities are separate. Bootstrap is opt-in and idempotent using the private stable operation UUID. Setup waits for authenticated Mongo quorum, all Redis slots/nine members and two linked replicas per primary, app readiness, two Envoy/controller placements and current route/policy conditions. Kind's missing external LoadBalancer address is expected; listener Programmed and actual service traffic provide the usable condition.

Run load, HA and credentials proofs **serially**, with one mutation owner. Do not rerun setup during a fault: it scales authz to zero while checking bootstrap dependencies. Root's actual repository publisher helper must be placed alongside these scripts (or passed explicitly):

Use the TLS-capable Python path appropriate to the host for the credential command. The combined coordinator now runs a mandatory healthy `verify-ha --phase baseline` before measured traffic/faults. Mongo baseline precedes publisher preparation; Redis identity preparation precedes its baseline. A failed or incomplete preflight prevents fault/load launch, and its cleanup is awaited rather than killed. This baseline remains a partial proof and does not count as full HA. The explicit post-Redis baseline above also makes operator home-role restoration visible.

The generator gets an invocation-owned policy allowing only CoreDNS and the exact Gateway workload and port. A failed positive backend control prevents all load/quota scheduling. Baseline gates are 100 scheduled requests/second for 60 seconds, achieved rate at least 99/second, p95 at most 100 ms, p99 at most 250 ms and at least 99.9% expected success. Latencies include dispatch delay; failed or omitted schedules remain in the accounting. The 300/600 requests/second phases characterize capacity without adding a performance SLO. Cold-control latency, 50 scheduled priming requests at 10 RPS, and 500 scheduled warmup requests at 100 RPS are retained separately. Priming and warmup must each return all expected exact-body 200 responses without omitted work before measurement starts. The unpaced cold 500-request burst exceeded the adapter admission bound in an earlier rejected run; paced warmup does not certify cold-start availability. The concurrent quota phase consumes its dedicated bucket: a rerun needs an explicitly fresh quota identity as well as a fresh HA identity. It never clears existing counters.

The resilience-load driver observes 100 RPS for 120 seconds across one actual primary fault. UTC milestones and a measured Pod/host clock bound align every scheduled/completed request with the fault window. Fail-closed 503 or transport errors inside the recovery window remain counted. Any wrong backend body, omitted/unaccounted schedule, unexpected status or failure wholly outside that window rejects the proof. The original automatic-fault failure window is never broadened for operator failback. The final 60 seconds must follow verified recovery and any performed role restoration and meet the original baseline bounds. Its partial proof does not replace the full HA run. The Mongo driver compiles and uploads only the actual packaged repository dependencies before scheduling load, then verifies the dedicated probe UID, source authz UID, exact local/deployed JAR hashes and unchanged policy pointer. Its publisher runs in a separate non-serving Pod with a 64 MiB heap and independent CPU/memory limits; it never starts a second JVM inside the authz cgroup. Owned probe policies allow only DNS and Mongo, and no Service selector may select the probe. Cleanup independently verifies the owned Pod and policies absent. The Redis driver automatically appends a fresh HA identity; the explicit preparation before full HA preserves all existing mappings/counters and the exact published pointer.

Two replicas with required hostname anti-affinity use zero surge and one unavailable replica for rolling updates; default percentages otherwise deadlock when only two workers are eligible. Credential proofs replace old authz/Envoy Pods, use fresh TLS/store connections and test certificate/CA, API-key, Mongo/Redis password and real Studio JWT/JWKS retirement. Successful rotation updates the private fixture files and Secrets; old logical counters and the published pointer remain intact. A 100 ms in-cluster backend sampler retains every status, latency, transport error and missed schedule during certificate, API-key and store rotations; observed gaps remain failures in availability evidence. A new Redis replica UID must start from the rotated Secret, preserve its PVC/data and actual cluster identity, link to its primary and reject retired credentials over fresh sockets. JWT checks include missing, expired, wrong issuer/audience/signature/algorithm and unknown-key rejection. Warm-cache acceptance of a retired signing key is recorded before an observed JWKS refresh and a fresh decoder reject it.

Credential results separate `protocol_passed`, `rotation_availability_passed`, `complete` and `final_acceptance_passed`. Availability requires nonempty observations for every requested sampled phase, exact schedule accounting, no omissions/errors/wrong bodies and verified sampler cleanup. An availability-only failure writes the result and exits nonzero while retaining successfully rotated credentials; it does not roll back a completed protocol change. A successful partial run still has `complete: false` and cannot establish final acceptance. JWT-only verification has no rotation-availability observations and does not pass that gate.

Authz uses Spring graceful shutdown with a 20-second timeout per shutdown phase. Its pinned Kubernetes 1.35 Pod uses a native ten-second preStop sleep and a 45-second termination grace period. The settling interval keeps the listener serving while terminating endpoints propagate; it is not a measured propagation guarantee. The Spring setting is per phase, so these values do not prove that every application shutdown phase and bean destruction fit the Pod budget. An actual embedded Tomcat regression holds an accepted request through context shutdown and verifies its complete HTTP 200 response. The immediate-shutdown baseline fails that regression. Envoy retains its Envoy Gateway generated shutdown-manager behavior.

TLS rotation also checks each of the two Ready Envoy Pod UIDs. Before changing the server leaf, both must have loaded the exact old-plus-new server CA set and old client certificate from the application cluster's bound active SDS secrets. Before retiring old client trust they must have loaded the new client certificate; the final barrier requires new-only trust. Comparisons use DER certificate fingerprint sets, distinguish active from warming resources, and reject unrelated xDS secrets. Each barrier then checks an authenticated exact-body backend response through each Pod. A late result fails the shared 90-second acceptance deadline. This establishes loaded active configuration and protected traffic; it does not prove wire ACK delivery or an independent new upstream TLS handshake. Private rotation action timelines and sampler UTC/monotonic anchors support diagnosis without logging command arguments, certificate material, credentials or exception messages. Cross-host clock agreement must be verified before using those anchors for precise causal attribution.

The HA script verifies four consumed quota permits, freezes the actual owning Redis primary through containerd, observes promotion, verifies one permit remains, then requires exactly one success and a 429. Replica script caches are flushed to prove real NOSCRIPT recovery. Authz process identities must stay unchanged during promotion. Continuous high-capacity traffic targets the same shard. Mongo primary freezing invokes the actual publication helper during election and verifies majority-visible metadata-only publication with unchanged epoch, quota and ACL. A timed-out no-quorum publication remains an **unknown outcome** until majority recovery explicitly resolves its operation ID and unchanged active pointer.

Pod replacement requires a genuinely new controller-owned UID, all desired replicas Ready, exact StatefulSet ordinal and unchanged PVC UID/mount. A small random sentinel on the actual mounted data volume proves content continuity; it is removed independently during cleanup. Worker testing stops the node hosting the active Envoy Gateway controller leader, requires a new Lease holder, patches the existing protected route with a unique response header, and requires new xDS configuration plus three consecutive real backend responses while Docker still reports the node stopped. The route is restored exactly. Redis `NOREPLICAS` write guard and whole-shard `CLUSTERDOWN` are separate failure checks. Mongo no-quorum publication is checked independently; previously committed reads need not fail.

The serving gateway preset keeps circuit breaking enabled with a five-second open wait and bounded half-open trial calls. The previous 30-second default delayed recovery beyond the 30-second RTO under 100 RPS even after Redis promoted in five seconds; lowering the configured reprobe interval preserves fail-closed behavior and the original acceptance bound. Promotion and Mongo recovery gates are 30 seconds; worker/Pod service recovery gates are 90 seconds. These are test acceptance bounds, not vendor RTO guarantees. Node restoration and final cleanup also require all three nodes, Mongo three healthy voters, all nine Redis members/slots with two online replicas per primary, and both app/backend/Envoy/controller replicas within one shared 180-second budget. Original route equality and actual header removal are checked before clearing restoration state. Only `ha.json` with `complete: true` **and process exit 0** is completed evidence; it is written after independent task/node/route/probe cleanup. An exception leaves progress evidence and fails the run. Python optimization is rejected because proof assertions must execute.

The first full HA run consumes its dedicated five-permit bucket. A full rerun requires a fresh private HA key and logical identity appended to the existing mapping, preserving load/quota/rotation identities. Coordinate that healthy preparation and authz rollout before taking the new baseline, update `ha_api_key_file` and `ha_api_key_id`, then retain the same authz UIDs throughout Redis failover. There is no hidden Redis deletion, WAIT workaround or counter reset. Do not interpret a partial phase as the full five-permit sequence.

PVCs protect local Pod replacement only; no off-host backup, whole-host resilience or production availability claim is made. Proof JSON records observed timing, placements, policy identity, raw bucket fields and restoration. Credentials must never be passed as shell literals, printed or committed.

The fixture URIs explicitly set `heartbeatFrequencyMS=2000`, `waitQueueTimeoutMS=2000`, `minPoolSize=4` and `maxConnecting=8` for the packaged Mongo Java driver alongside the two-second connect, selection, socket and write-concern limits. These bound connection checkout and prewarm connections; the actual packaged driver parsed both application and administrator URIs to the intended settings before rollout. They increase monitoring, authentication and connection work and do not change replica-set election timing or impose one overall publication deadline. The minimum pool size applies per server and per client. A full publication/replay/Gateway sequence exceeded the original 30-second gate with both the default and tuned monitoring/pool configuration; those attempts remain rejected. Pool starvation has not been established as their cause. Only a fresh passing run establishes the observed RTO. Streaming `hello` and request-triggered checks mean the default ten-second heartbeat is not a fixed detection delay.

Redis and Mongo automatic-recovery proofs require at least ten exact-body Gateway successes spanning two seconds while the fault remains active. Any failure resets the success window; simultaneous sampler failures reject it. The combined Redis observation defers optional operator home failback until observation ends. The explicit baseline command above restores home primaries before the next fault. It must not be used to broaden the measured automatic-recovery window. Load and HA body checks accept only the exact backend body or its single terminal LF; whitespace, extra prefixes/suffixes and incomplete bodies reject the proof.

Dense recovery streams a READY marker and anonymous partial observations. Tool startup and the READY exchange consume the original root acceptance budget; the remote receives only its remaining time, anchored at its earlier READY. A timeout or late final result remains failure even if it contains successful requests. Whitelisted timings distinguish RPC startup, response-header time and body-read time; header time also includes DNS/connect work. Blocking I/O or cleanup may delay failure return beyond the acceptance deadline but cannot authorize a late PASS or extend the measured fault window.

Authz resolves one immutable policy snapshot per request, rejects unsupported blocking policies before consumption, and executes that exact snapshot through the existing engine. Readiness still checks the provider separately. Custom embedding must treat the Authz-injected provider as authoritative; an engine with a different provider does not replace the supplied snapshot.

Publication initializes its three existing secondary indexes in one `createIndexes` command with the same keys, default index options and inherited majority write concern. Earlier fault logs showed repeated serial majority waits in separate initialization commands after a writable primary already existed; writable-primary election and majority replication recovery are distinct milestones. The batched command reduces redundant barriers without skipping indexes, weakening writes or guaranteeing the end-to-end recovery deadline. The private publisher proof retains per-attempt UTC and monotonic timing plus whitelisted repository class/method/line fields, never exception messages or connection details.

The adapter limits admitted decisions to `fluxgate.envoy.max-concurrent-decisions` (positive integer, default 32) per Pod. Admission never queues: overload returns 503 before policy I/O, quota consumption or event recording. Every admitted exit releases the permit, including exceptions and errors. This preserves the existing snapshot/ACL/key/limiter/event path for admitted requests; it changes overload throughput and is not an overall request timeout. Readiness remains separate. Tune capacity against measured workloads rather than interpreting fast 503 responses as recovery.

When the optional management listener is enabled, `GET /diagnostics` exposes only process-lifetime numeric decision counters and six fixed 503 categories, without policy/engine/readiness I/O. It exposes no identity, policy, request or exception values and is not a Prometheus exporter. Restrict the plaintext management listener with the existing management NetworkPolicy. Counts reset with the Pod process; concurrent snapshots are observational, and completed service calls do not prove delivered HTTP responses. Compare counters with exact Pod UIDs and timed request evidence before attributing an error.

The network proof uses a temporary Gateway-namespace control Pod with the two policy identity labels, without matching the real Gateway Service selector. Those labels also match the existing Envoy Pods’ required anti-affinity. In this three-node local fixture the control selects the validated single control-plane node and tolerates only its control-plane NoSchedule taint. No serving Pod placement or NetworkPolicy is relaxed.


The Envoy adapter keeps ordinary request statistics off the decision thread only for the exact built-in Mongo recorder, including its built-in composite wrapper. Its bounded dispatcher has four workers and a 1,024-event queue with rejection, no caller-runs fallback, bounded immutable event copies and a bounded shutdown drain. `GET /telemetry` on the optional management listener exposes numeric accepted/succeeded/failed/rejected/cancelled/inflight/queue/outstanding counts. Custom recorders retain their existing synchronous behavior. Request statistics are best effort: overload, store failure or termination can lose records and delivery can reorder them. This is not the majority-committed policy audit. See [the telemetry contract](../../fluxgate-envoy-extauth/TELEMETRY.md).

The credential sampler uses independent fixed 100 ms arrivals, up to 24 fresh-connection workers and no hidden retries. It records latency from scheduled arrival, explicit lateness/capacity omissions, worker failures and pending sequences. Stopping prevents new submissions and drains accepted work before collection; any omission, pending work, incomplete drain, non-200 response, unexpected backend body or cleanup failure rejects availability. The earlier sequential generator's observed omission remains a rejected control rather than being removed from the history.

The selected Envoy Gateway 1.9.2 enables HCM path normalization before HTTP filters and routing. Exact path rules depend on the gateway/backend agreeing about path interpretation. The local exhausted-key control and four unreserved-percent-encoded variants of `/api/quota` all returned 429 through the live Gateway. This covers those variants on this configuration, not every backend decoding behavior or a custom xDS override. See the [pinned translator](https://raw.githubusercontent.com/envoyproxy/gateway/v1.9.2/internal/xds/translator/listener.go).

The isolated Envoy and Studio artifacts use patched Spring Boot 3.5.16 and locally constrained dependency versions; the Studio OpenAPI integration is separately covered by actual MVC/security regression tests. Boot 3.5.16 was the final OSS 3.5 release, not an ongoing OSS support commitment. This fixture does not provide a full OS/JRE/transitive vulnerability scan or production support approval. Current evidence and remaining release gates are recorded in the [expanded review](../../docs/reviews/2026-10-10-enterprise-resilience-review.ko.md).


API-key rotation now checks each of the two Ready, nonterminating authz Pod UIDs directly over verified fresh mTLS connections after old-only, overlap and retirement mapping rollouts. Each pinned Pod must give the exact expected old/new/missing/wrong-key status on the high-capacity load path; these controls do not consume the five-permit quota bucket. A changed UID, unavailable replica, transport failure or late result rejects the shared 90-second barrier and follows the existing failure rollback. Gateway-routed quota controls independently prove shared logical identity and preserved consumption.

For the reviewed Studio Security 6.5.11 / Nimbus 9.37.4 artifact, the default Nimbus JWK cache TTL is 300 seconds; refresh ahead is disabled. Its 15-second refresh-lock wait timeout is not a refresh interval, retrieval deadline or maximum key-revocation time. The previously recorded 900-second lifespan described a deprecated cache implementation and is superseded in the latest proof metadata. The actual cached acceptance and post-refresh/cold-decoder retirement observations remain separate facts.
