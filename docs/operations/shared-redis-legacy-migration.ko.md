# 공용 Redis: 0.3.x 전환 검증 근거와 릴리스 조건

[English](shared-redis-legacy-migration.md) · [Published-epoch 모드](shared-redis-published-epochs.md)

## 상태와 검증 범위

이 문서는 검증 근거와 전환 체크리스트이며, **지원이 확정된 롤링 업그레이드 절차가 아닙니다**.
2026-11-18(KST)에 공식 발행된 0.3.7·0.3.8 아티팩트와 PR #79의 후보 커밋
`837b40c2faae80ccc6a3ad56209cdae96cca2ee9`를 비교했습니다. 실제 Lua 리소스와 해당
키·호출 형식을 격리 Redis에서 시험했습니다. 구·신버전 Java 애플리케이션 전체,
실제 Pod, 운영 트래픽 또는 Redis Cluster를 실행한 시험은 아닙니다.

공용 Redis 사용이 목표이며 전용 Redis는 필수 조건이 아닙니다. `PUBLISHED_EPOCH`는
명시적으로 선택하는 모드이고 기본값은 `LEGACY_RESET`입니다. 모드 이름만으로 공식
0.3.x의 카운터 상태와 호환된다고 판단해서는 안 됩니다.

## 아티팩트 식별

공식 발행 좌표는 다음과 같습니다.

- `io.github.openfluxgate:fluxgate-redis-ratelimiter:0.3.7`
- `io.github.openfluxgate:fluxgate-redis-ratelimiter:0.3.8`

두 바이너리 JAR을 공식 Maven Central에서 별도로 내려받고 게시된 `.jar.sha1`과
일치하는지 확인했습니다. 아래 SHA-256은 재현을 위해 직접 계산한 값이며,
전자서명 검증을 수행했다는 의미는 아닙니다.

| 버전 | 공식 아티팩트 디렉터리 | 게시 값과 일치한 SHA-1 | 직접 계산한 JAR SHA-256 |
| --- | --- | --- | --- |
| 0.3.7 | [Maven Central](https://repo.maven.apache.org/maven2/io/github/openfluxgate/fluxgate-redis-ratelimiter/0.3.7/) | `0958ee55bfa7b4371911cc049c7b29bef9e79395` | `92cc7321df451f9b6c5ac850173210fff078ce0461f2e03f2d49a940702d3490` |
| 0.3.8 | [Maven Central](https://repo.maven.apache.org/maven2/io/github/openfluxgate/fluxgate-redis-ratelimiter/0.3.8/) | `074b793bd71014777ff5f5ae0497fc08fc1b7742` | `3411aee46646e7981a0accd9b0da7b705ebbbcbd0914746bf5a2d96d92d8299e` |

두 공식 버전의 `lua/token_bucket_consume.lua`는 바이트 단위로 동일하며 SHA-1은
`c50421ad02e1b7e96852b75332174af1d7491c20`입니다. 시험한 후보 스크립트의 SHA-1은
`b3bf3d0b4f3ee8db6f4b03e2da46804f02291b8c`입니다.

로컬 Maven 캐시 디렉터리나 버전 문자열만으로 아티팩트를 식별하지 마십시오.
로컬 install은 릴리스 좌표를 덮어쓸 수 있습니다. 검토 중 캐시의 0.3.7 JAR 하나가
저장된 공식 체크섬과 달라 시험에서 제외했습니다. 캐시 자체는 변경하지 않았습니다.
불일치의 원인을 단정할 필요 없이 별도로 검증한 공식 아티팩트를 사용했습니다.

## 서로 다른 카운터 형식

| 항목 | 공식 0.3.7 / 0.3.8 | 시험한 0.5.0 후보 |
| --- | --- | --- |
| 버킷 키 | `fluxgate:<set>:<rule>:<identity>:<label>` | `fluxgate:bucket:{<set>:<rule>:<identity>}:<band-label>`, legacy가 아닌 세대에는 epoch 접미사 추가 |
| 토큰 버킷 시각 | `last_refill_nanos` | `last_refill_micros` |
| 소비 호출 형식 | 버킷 하나; 용량·나노초 단위 윈도·요청량 | FENCED 버킷·메타데이터·펜스 키; 밴드 설정·revision·플래그 |
| 반환 값 | 4개 | 8개 |

신규 메타데이터와 revision 펜스가 구버전 키를 동일한 할당량에 참여시키지는 않습니다.
epoch가 문자열 `legacy`이면 epoch 접미사를 생략할 뿐, 공식 0.3.x의 키·시각 형식으로
돌아가지 않습니다. 밴드 라벨의 자동 생성·이스케이프 방식도 같다고 가정하지 말고
각 기존 규칙에 대해 확인해야 합니다.

## 격리 환경에서 확인한 반례

새로 만든 단기 `redis:7-alpine` 컨테이너에 네트워크 비활성화, 외부 포트 미게시,
메모리 64 MiB, CPU 0.25 제한을 적용했습니다. 영속화는 끄고 소수의 스크립트 호출만
수행했습니다. 소유한 컨테이너를 제거한 뒤 실제로 남아 있지 않음을 확인했습니다.
기존 Redis 인스턴스나 운영 URI는 사용하지 않았습니다.

정책은 용량 **5**, 충전 윈도 **3,600초**의 토큰 버킷입니다. 연속 호출 사이에 토큰
하나가 충전될 시간은 없었습니다. 구버전 호출에는 공식 0.3.8 스크립트를 사용했으며,
0.3.7과 동일하므로 두 버전에 같은 스크립트 수준 결과가 적용됩니다. 신규 호출에는
후보의 실제 FENCED Lua 프로토콜, revision 1, 소스에서 확인한 버킷·메타데이터·펜스
키 이름을 사용했습니다.

### A. 구·신버전 writer가 할당량을 분리해서 사용

| 단계 | 실제 결과 |
| --- | --- |
| 구버전 키에서 5개 소비 | 허용, 잔여 토큰 0 |
| 구버전 키에서 1개 추가 요청 | 거절, 잔여 토큰 0 |
| 같은 논리 할당량의 신규 키에서 5개 소비 | 별도 버킷에서 허용, 신규 잔여 토큰 0 |

의도한 하나의 한도 5에 대해 두 키 공간에서 **5 + 5개가 허용**됐습니다.
소진된 구버전 해시에는 `last_refill_nanos`, 신규 해시에는 `last_refill_micros`가
저장됐습니다. 빌드나 기동 성공만으로 이 할당량 분리가 방지되지는 않습니다.

### B. 키 이름만 바꾸면 이미 소비한 할당량이 보존되지 않음

두 번째 구버전 버킷에서 5개를 모두 소비한 뒤, 격리 인스턴스 안에서만 그 해시를
신규 버킷 이름으로 변경했습니다. 이후 후보 FENCED 스크립트가 **다시 5개를 허용**했습니다.
구버전 해시에 `last_refill_micros`가 없으므로 신규 코드가 가득 찬 버킷으로 초기화한
것입니다. 키 이름만 바꾸는 전환은 이미 소비한 할당량을 보존하는 변환이 아닙니다.

이 결과는 반례이며 처리량 벤치마크도, 가능한 모든 전환 방식이 실패한다는 증명도
아닙니다. 다만 구·신버전이 한도를 공유한다고 약속하거나 단순 rename을 호환 전환으로
간주해서는 안 되는 이유를 보여줍니다.

## `validateLegacyBootstrap()`이 보장하지 않는 것

`MongoPolicyRepository.validateLegacyBootstrap()`은 기존 Mongo 규칙 문서와 최초 발행
규칙의 구조·용량 등을 비교합니다. 실제 Redis writer 바이너리, 키 형식, 시각 단위,
이미 소비한 토큰 상태는 검사하지 않습니다. 이 검사 통과는 공식 0.3.x에서 이미 소비한
할당량이 보존됐다는 증거가 아닙니다. 메서드나 epoch에 쓰인 `legacy`라는 단어는
버전을 협상하는 장치가 아닙니다.

## 운영 전환의 필수 조건

1. **대상 식별:** 실제 배포 아티팩트·체크섬, 같은 할당량을 쓰는 애플리케이션과 Pod,
   정책 설정·라벨·초기화 작업·Redis 상태 형식을 확인합니다. 자동 확장, 예약 작업,
   재해 복구용 인스턴스도 포함합니다.
2. **변경 동결과 복구:** 정책·설정·상태의 일관된 백업을 준비하고 격리 환경에서 복구를
   검증합니다. 전환 중 정책 변경과 파괴적인 초기화를 동결합니다. 일부 키 표본을
   전체 키 목록으로 간주하지 않습니다.
3. **기존 writer 차단:** 영향받는 요청의 유입을 멈추거나 승인된 트래픽 차단을 적용합니다.
   진행 중 요청·재시도·큐를 비우고 구버전 writer가 재개되지 않음을 확인합니다.
   자동 확장이나 자동 롤백으로 구버전이 복귀하지 않도록 합니다.
4. **신규 트래픽 전에 사용량 처리 방침 확정:** 별도로 구현·검증한 상태 변환기로 이미
   소비한 할당량을 보존하거나, 초기화와 추가 버스트 가능성을 명시적으로 승인받습니다.
   **이 PR은 0.3.x 상태 변환기를 제공하지 않습니다.** 자연 충전이 끝날 때까지 기다리는
   방식도 정책별 시간 상한의 검증과 서비스 가용성 계획 승인이 필요합니다. 키 만료만으로
   사용량이 안전하게 보존됐다고 판단해서는 안 됩니다.
5. **신규 대상 검증:** published provider와 실패 시 차단 조건을 명시적으로 설정합니다.
   신규 인스턴스가 한도를 공유하는지, 보존·초기화가 의도대로 동작하는지, 오래된 writer가
   차단되는지, Redis·Mongo 부하가 허용 범위인지 확인한 뒤 트래픽 차단을 해제합니다.
6. **관측:** 실제 판정 건수·정책 버전·오류·Redis 메모리와 지연·Mongo 조회량을 확인합니다.
   구 상태 정리는 현재 카운터를 선택하지 않는 소유권 기반 절차로만 수행합니다.
   공용 인스턴스 전체를 지우는 방식은 사용하지 않습니다.

이 체크리스트 자체는 운영 작업을 승인하지 않습니다. 선택한 사용량 보존·초기화 방침,
트래픽 영향, 중단 조건과 담당자를 배포 계획에 남겨야 합니다.

## 롤백 필수 조건

바이너리만 낮추는 것은 안전한 롤백이 아닙니다. 신규 버전이 트래픽을 처리한 뒤에는
구 상태나 전환 전 백업이 오래된 상태가 되어 추가 요청을 허용할 수 있습니다.
먼저 트래픽과 양쪽 writer를 차단하고, 이미 소비한 할당량을 정합하게 맞추거나 명시적으로
초기화를 승인받아야 합니다. 그 후 호환되는 정책·상태·설정 조합을 복구하고 검증한 뒤
트래픽을 재개합니다. 이 절차가 준비될 때까지 구버전 writer 복귀를 막아야 합니다.
안전한 롤백을 입증하지 못했다면 릴리스 차단 조건이며, 구버전 전체를 조용히 재기동하는
근거가 아닙니다.

## 이 근거만으로는 검증되지 않은 항목

- 진행 중 요청이 있는 전체 Java 애플리케이션·다중 Pod 업그레이드와 롤백.
- 모든 지원 알고리즘·라벨·상태 변형에서 사용량을 보존하는 변환기.
- 신규 모드 Pub/Sub 유실·순서 뒤바뀜·재연결의 end-to-end 동작.
- 전환 중 Redis Cluster 장애 조치·재분배·revision 펜스 만료.
- 수백만 키 공용 Redis 부하, Mongo QPS·지연·장애 영향, 요청 꼬리 지연.
- 실제 운영 백업·복구와 조직의 트래픽 차단 장치.

별도 검증 결과는 정확한 커밋과 함께 관리해야 합니다. 다른 시험이 성공했다는 이유만으로
이 문서에 남은 릴리스 조건까지 충족한 것으로 간주하지 않습니다.
