FluxGate를 K8s 라우터의
요청 판정 지점에 연결하기

목표는 Java·Go·Rust 서비스에 SDK를 심지 않고, 외부에서 들어오는 HTTP 요청을 Envoy Gateway에서 공통 제한하는 것이다. FluxGate는 기존 Java 규칙 엔진과 Redis 카운터를 사용하는 판정 서비스로 둔다.

권장 결정

Envoy Gateway의 SecurityPolicy.extAuth를 1차 통합 지점으로 선택한다. 요청별 판정은 FluxGate Java 서비스가 소유하고, Redis의 소비 결과를 HTTP 상태로 반환한다. Envoy는 허용된 요청만 기존 서비스 Pod로 전달한다.

판정 서비스는 현재 존재하지 않는 새 컴포넌트다. 기존 FluxGate의 규칙·키·제한 알고리즘을 재사용해 만든다. 정책을 HTTPRoute에 부착하기 전까지 기존 서비스의 요청 경로는 변하지 않는다. Go나 Rust로 판정 서비스를 다시 작성해도 Envoy→판정 서비스, 판정 서비스→Redis 호출은 사라지지 않는다. 서비스 구현 언어와 제한 정책을 분리하는 것이 핵심이다.

범위: Gateway를 통과하는 HTTP 트래픽. Pod 간 직접 호출, 비HTTP 트래픽, 배치 작업은 자동으로 보호되지 않는다.

요청 한 건의 순서

시퀀스를 전체 화면으로 열기 ↗

제한을 초과하면 FluxGate가 429를 반환하고 Envoy는 원 서비스에 요청을 보내지 않는다. 제한 카운터는 서비스의 비즈니스 처리 성공과 무관하게 판정 시도 시점에 소비된다. 현재 Redis 소비 원자성은 한 규칙의 band 묶음에만 적용된다. 여러 규칙이 매칭되면 앞선 규칙에서 카운터를 소비한 뒤 뒤쪽 규칙이 거절할 수 있다. 파일럿은 매 요청에 제한 규칙 하나만 매칭되도록 제한하고, 다중 규칙 전체의 의미는 별도 설계한다.

왜 이 확장 지점인가

1. SecurityPolicy.extAuth요청 전체 문맥을 보고 FluxGate가 허용·403·429를 결정한다. 기존 엔진·Redis 의미를 보존하기 쉽다. 매 요청 동기 네트워크 호출이 생기고 Envoy 전용 정책 CRD를 쓴다.
2. BackendTrafficPolicy global rate limitEnvoy의 정식 트래픽 정책에 잘 맞고 공유 버킷·shadow mode·비용 설정이 있다. 그러나 기존 FluxGate의 ACL·규칙 우선순위·알고리즘·Redis 키를 그대로 재사용하는 연결은 아니다.
3. Envoy RLS 프로토콜 어댑터장기적으로 rate limit 전용 인터페이스와 결합할 수 있다. domain + descriptors + hits_addend 계약, 정책 descriptor 생성, 배포 연결을 새로 설계해야 한다.

Gateway API의 라우팅 리소스와 판정 API는 분리할 수 있지만, SecurityPolicy 바인딩은 Envoy Gateway 전용이다. Experimental HTTPRoute.externalAuth 지원 여부는 배포할 컨트롤러 버전에서 확인한다.

프로토콜 함정: 기존 샘플의 200 {"allowed":false}를 Envoy에 연결하면 허용으로 처리된다. 샘플 API를 재사용하지 말고 extAuth 전용 HTTP 응답 어댑터를 둔다.

규칙 누락·매칭 규칙 없음·잘못된 설정명시적 거부 및 운영 알림현재 limiter는 규칙이 하나도 매칭되지 않거나 band가 비었으면 허용한다. extAuth 어댑터는 이를 보호 경로의 정상 허용과 구분해야 한다.

Envoy의 extAuth 기본 timeout은 서비스 경로에 비해 길 수 있으므로 명시적으로 제한한다. 목표치는 실제 요청 지연·Redis 지연·재시도 분포를 측정한 뒤 정한다. 이 판정 호출은 모든 허용 요청의 지연에 포함되므로 수평 확장, connection reuse, health check, 과부하 보호가 설계 일부다.

정책 우회를 막는 경계

  1. 사용자 신원: X-User-Id 같은 클라이언트 입력을 신뢰하지 않는다. Gateway 또는 신뢰된 앞단에서 인증하고, 전달 헤더를 제거·재작성한 뒤 판정 서비스에 보낸다.
  2. 클라이언트 IP: 프록시 체인과 신뢰 프록시 범위를 명시한다. 사용자가 만든 X-Forwarded-For를 그대로 카운터 키로 쓰지 않는다.
  3. 경로 연결: 정책을 Gateway 전체에 붙일지 HTTPRoute별로 붙일지 정한다. Route 정책이 Gateway 정책을 가릴 수 있으므로 새 Route의 보호 여부를 배포 검증에 포함한다.
  4. 직접 호출: 모든 진입을 제한하려면 서비스 Pod/ClusterIP에 대한 직접 접근을 NetworkPolicy 등으로 제한한다. 내부 서비스 간 호출은 별도 정책 영역으로 정의한다.
  5. 격리: 판정 endpoint는 외부 공개 Route에 싣지 않는다. Envoy→FluxGate와 FluxGate→Redis 접근만 허용하고 인증·TLS 요구는 클러스터 위협 모델에 맞춰 정한다.

로컬 테스트: Java 판정 서비스와 Envoy 연결 확인

판정 서비스와 배포 예제를 구현했다. 재현 가능한 명령은 로컬 배포 가이드와 파일럿 매니페스트에 있다. 아래 공식 모의 서비스 절차는 Envoy 자체를 따로 살펴볼 때 참고한다.

2026-10-10 실측: Docker Desktop 위의 별도 kind-fluxgate-eg 클러스터(Kubernetes 1.35)에서 Envoy Gateway 1.9.2를 설치했다. Java 판정 서비스, Redis, Echo Pod가 준비된 뒤 Gateway 경유 요청은 200 → 200 → 429였고, 거부 응답에 Retry-After: 30이 있었다. Redis Pod 중단은 GET과 OPTIONS 모두 503, 전역 키 ACL 거부 프로필은 403을 반환했다. 판정 Pod를 0개로 줄여 엔드포인트를 없애자 Envoy는 500을 반환하며 차단했다. kind에서 외부 주소가 없어 Gateway 최상위 Programmed=False였지만 listener와 Route·SecurityPolicy는 수락됐고 포트포워드로 요청을 검증했다.

1. Java 엔진과 Redis를 먼저 확인

./mvnw -pl fluxgate-core,fluxgate-redis-ratelimiter -am test
./mvnw -pl fluxgate-core,fluxgate-redis-ratelimiter -am verify

이 브랜치에서 실제 실행 결과: core unit 536건, Redis unit 248건 모두 통과. Redis integration 65건 중 실패 0건·건너뜀 6건이다. 건너뛴 6건은 별도 Redis Cluster 테스트 설정이 필요한 케이스다. 이 결과는 Envoy 연동 성공을 뜻하지 않는다.

공식 quickstart의 echo 서비스와 버전 고정 extAuth 데모를 연결하면, 새 FluxGate 서비스 없이도 Envoy가 200 허용과 403 거절을 서비스 호출 전에 처리하는지 볼 수 있다. 데모는 제품 구현으로 사용하지 않는다.

다음 SecurityPolicy를 /tmp/fluxgate-eg-securitypolicy.yaml에 저장한다. 파일럿 Route 하나에만 붙이므로 기존 서비스 경로에는 영향이 없다.

apiVersion: gateway.envoyproxy.io/v1alpha1
kind: SecurityPolicy
metadata:
  name: local-http-auth
  namespace: default
spec:
  targetRefs:
    - group: gateway.networking.k8s.io
      kind: HTTPRoute
      name: backend
  extAuth:
    failOpen: false
    http:
      backendRefs:
        - name: http-ext-auth
          port: 9002
kubectl --context kind-fluxgate-eg apply -f \
  https://raw.githubusercontent.com/envoyproxy/gateway/v1.9.2/examples/kubernetes/ext-auth-http-service.yaml
kubectl --context kind-fluxgate-eg apply -f /tmp/fluxgate-eg-securitypolicy.yaml
kubectl --context kind-fluxgate-eg wait securitypolicy/local-http-auth \
  --for=condition=Accepted --timeout=2m

ENVOY_SERVICE=$(kubectl --context kind-fluxgate-eg get service \
  -n envoy-gateway-system \
  -l gateway.envoyproxy.io/owning-gateway-namespace=default,gateway.envoyproxy.io/owning-gateway-name=eg \
  -o jsonpath='{.items[0].metadata.name}')
kubectl --context kind-fluxgate-eg port-forward \
  -n envoy-gateway-system "service/$ENVOY_SERVICE" 8888:80

port-forward를 켜 둔 채 다른 터미널에서 아래 두 요청을 보낸다. 첫 요청은 인증 데모의 403, 두 번째는 200과 echo 응답이어야 한다. 이것이 Envoy 정책 연결의 증거이지 FluxGate 제한 기능의 증거는 아니다.

curl -i -H 'Host: www.example.com' http://127.0.0.1:8888/get
curl -i -H 'Host: www.example.com' \
  -H 'Authorization: Bearer token1' http://127.0.0.1:8888/get

3. FluxGate 판정 서비스로 교체한 결과

파일럿 HTTPRoute에 새 Java extAuth 서비스를 연결했다. 규칙은 서버가 소유하는 단일 전역 버킷(2회/60초)이다. 전달받은 IP·사용자·rule-set 헤더로 사용자를 나누지 않는다. 서로 다른 위조 X-Forwarded-For 세 값으로 호출해도 200·200·429였다. 따라서 사용자별 제한은 아직 구현 범위 밖이다. 단위 테스트는 매칭 없음·중복 매칭·Redis 실패를 503으로 처리하는지 확인했다.

호출예상확인할 증거
정상 요청 2건200echo 응답 2건, Redis 카운터 2회 소비
같은 키의 3번째 요청429echo 호출 0건 증가, Retry-After 확인

버전 선택 근거: Envoy Gateway v1.9.2의 공식 호환 범위는 Kubernetes 1.33–1.36이다. kind 노드는 1.35로 고정했다. kind 기본 CNI는 NetworkPolicy를 강제하지 않으므로 내부 직접 호출 차단은 검증되지 않았다. 이 실험용 클러스터는 kind delete cluster --name fluxgate-eg로 정리할 수 있다.

구현 순서와 통과 기준

  1. 격리된 파일럿: 새 판정 서비스를 별도 브랜치와 테스트 HTTPRoute에서 만든다. 기존 서비스의 라우팅 정책은 바꾸지 않는다.
  2. 정합성 게이트: 실제 트래픽에 연결하기 전 ACL, Mongo 저장, Redis window, provider 결합 등 앞선 리뷰 항목을 최신 커밋에서 재검증한다. 이 결과 없이 보안 판정 서비스로 선언하지 않는다.
  3. 작은 어댑터: Java FluxGate에 전용 extAuth HTTP endpoint를 추가한다. 샘플 controller가 아닌 엔진을 호출하고 상태 코드 계약을 테스트한다.
  4. 실제 Envoy 연결: 배포 버전의 CRD를 고정하고 SecurityPolicy를 한 테스트 HTTPRoute에만 적용한다. 원 경로·method·identity 전달을 기록한다.
  5. 장애 실험: 허용, 403, 429, FluxGate timeout, Redis down, 잘못된 헤더, 우회 경로, 중복 호출, 매칭 규칙 없음·빈 band를 Envoy 경유로 확인한다. GET·POST·PATCH와 URL rewrite도 포함한다.
  6. 확장: 지연·오류율·정책 누락을 관측한 뒤 점진적으로 Route 범위를 넓힌다. 서비스별 SDK는 필요한 내부 호출에만 남긴다.
출시 전 미결정: 어느 신원 공급자가 user/tenant ID를 보증하는지, 내부 호출도 제한할지, 판정 서비스와 Redis 장애 때 어느 요청을 예외적으로 허용할지, 허용 응답의 카운터 소비를 중복 호출에서 어떻게 다룰지 합의가 필요하다.
