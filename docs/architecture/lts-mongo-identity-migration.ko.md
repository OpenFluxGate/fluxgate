# LTS Mongo 규칙 ID 이행

LTS `0.4.0-SNAPSHOT`의 규칙 ID는 `(ruleSetId, id)` 쌍입니다. 구버전의 unique `id_1`은 전역 ID를 강제해 이 계약을 막습니다. 양쪽 스타터의 CREATE와 VALIDATE는 이 제약을 발견하면 명시적 이행 오류로 시작을 중단합니다. 시작 과정에서 인덱스를 삭제하지 않습니다.

독점 유지보수 구간에서 다음 순서로 이행합니다.

1. 백업을 확인하고 인덱스 정의, 활성 정책 포인터와 관련 Redis 카운터를 기록합니다. 모든 구버전 writer와 동시 스키마·인덱스 관리 작업을 중지합니다. DDL 전에 판정 서비스를 중지하며 이 구간에는 요청이 불가할 수 있습니다.
2. 새 Mongo 어댑터와 명시적으로 권한을 부여한 유지보수 Mongo 클라이언트에서 `new MongoRateLimitRuleRepository(ruleCollection).migrateLegacyGlobalIdConstraint()`를 호출합니다. 실제 기존 규칙 컬렉션과 majority write concern을 사용합니다. 유지보수 자격증명을 서비스나 로그에 노출하지 않습니다.
3. 메서드는 수정 전에 사용자 정의 전역 ID 제약과 알려진 인덱스의 정확한 정의를 검사합니다. unique `(ruleSetId, id)`를 먼저 생성·검증하고, 알려진 단순 unique `id_1`만 제거한 뒤 nonunique `id_1` 조회 인덱스를 만듭니다. 규칙 문서·ACL·활성 정책 포인터·Redis 상태는 변경하지 않습니다.
4. 최종 인덱스 두 개와 문서 보존을 확인합니다. 반복 호출은 멱등적입니다. DDL 실패 시 writer를 계속 중지하고 오류를 비공개로 확인한 뒤 원인을 해결하고 재시도합니다. 구버전 인덱스 제거 후 실패해도 검증된 복합 제약이 ID를 보호합니다. 사용자 정의 인덱스는 운영자가 별도로 검토하며 자동으로 삭제하지 않습니다.
5. 새 서비스 산출물을 기동하고 시작·readiness·실제 백엔드 응답·정책 포인터 동일성·할당량 보존을 확인한 뒤 트래픽과 새 버전 writer를 재개합니다.

MongoDB 인덱스 삭제는 동시 DDL을 원자적으로 배제하지 못하므로 위 독점 구간은 운영 전제입니다. 구버전 JAR로 돌아가는 것만으로 이행이 되돌아가지 않습니다. 서로 다른 rule set에서 같은 ID를 사용한 뒤에는 데이터 조정 없이 전역 unique 인덱스를 복원할 수 없습니다.

Redis 키 인코딩과 정책 epoch·fence는 별도 호환성 문제입니다. 특수문자·예약 표기·일부 긴 identity는 구버전과 LTS의 키가 달라지며 자동 카운터 이행은 제공하지 않습니다. 새 lifecycle로 발행하기 전에 구버전 Lua 호출자를 업그레이드하거나 중지해야 합니다.
